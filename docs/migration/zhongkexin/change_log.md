# 中科芯平台迁移不兼容与修改台账

## 文档定位

本文档用于记录中科芯平台迁移过程中发现的关键不兼容点、关键修改点、暂缓点和 fallback。它是迁移过程的强制台账，不是日常操作流水账。

迁移期间不得只把关键问题记录在聊天记录、终端输出或个人笔记中。凡是影响构建、运行、数值、性能、报告、测试结论或协作方式的差异，都必须进入本文档。

## 迁移技术总结

本次迁移的核心目标不是把工程“能编译”到中科芯平台，而是把原始 CUDA C++ 信号处理库在当前项目公开接口、任务 demo、单算子测试、报告、图件和 benchmark 范围内完整迁移到中科芯 ZQ500。最终验收口径固定为 CPU reference + 容器内 ZQ500 GPU，不再要求 NVIDIA 路径作为阶段关闭条件。

整体迁移路线如下：

1. 先确认平台边界。宿主机只能作为文件中转和静态检查环境，真正构建、运行和验收都必须在本队 docker 内完成。中科芯 SDK 通过 `/zq500/sdk/env.sh` 激活，但该脚本无参 source 会读取 `$1` 并在 `set -u` 下失败，因此所有统一脚本都改为内部使用 `source /zq500/sdk/env.sh ""` 的兼容形式。宿主机到容器同步不直接覆盖 `/CETC`，而是复制到 `/CETC.incoming.<timestamp>`，再由容器内 `replace_container_project.sh` 原子替换，保证宿主机删除的文件也能从容器项目中消失。

2. 重建构建工具链入口。原项目默认依赖 NVIDIA CUDA Toolkit、`nvcc`、`CMAKE_CUDA_ARCHITECTURES=80` 和标准 `CUDA::cudart`/`CUDA::cufft` targets；中科芯 SDK 的目录、库名和编译器行为不同，不能直接复用这一路径。迁移后通过 `CUSIGNAL_PLATFORM=ZHONGKEXIN` 显式选择平台，构建统一使用 `/zq500/sdk/bin/dlcc` 作为 CXX 编译器，并把 `.cu` 源按 CXX 源交给 `dlcc -x cuda --cuda-gpu-arch=dlgput64` 编译，避免 CMake 生成 NVIDIA `sm_80` 或 `nvptx64-nvidia-cuda` 相关参数。CMake 侧增加平台兼容层，解析中科芯 runtime/FFT/BLAS/SOLVER 库，使用 `libcurt.so`、`libdlfft.so`、`libdlblas.so`、`libdlsolver.so` 等兼容库完成链接。

3. 收敛 ZQ500 GPU API 和第三方依赖。复赛说明显示中科芯 runtime/driver API 不是 CUDA 11.7 全量覆盖，cuFFT 只支持 2 的整数次幂，cuSOLVER LU pivot 不能传 `nullptr`。迁移时把这些约束写入 README、AGENT 和阶段计划，并在 probe、单测和任务依赖矩阵中逐步覆盖。源码中移除了 CUB/Thrust 依赖，因为相关头文件会生成 NVIDIA PTX inline asm，改为自写 kernel 完成 flag compaction 和 max reduce。FFTW、`numpy`、`matplotlib`、`scipy` 被纳入统一依赖准备，缺失时使用项目内 wheel 缓存或用户态安装，避免可视化和数据生成被静默跳过。

4. 针对数值差异做平台分支，而不是修改公开 API。spectrogram 和 csd 的 R2C PSD 快路径在中科芯 `dlfft` 上出现明显数值偏差，但同类 C2C 路径稳定，因此仅在 `CUSIGNAL_PLATFORM_ZHONGKEXIN` 下让相关 PSD/CSD 路径改走 C2C，NVIDIA 历史路径不作为当前验收口径。`wiener` 的自动噪声估计先做 D2H 标量同步再执行 GPU apply，同时把设备端局部窗口统计中的无符号倒序遍历改为显式有符号循环，规避 `dlcc` 对 `std::size_t dim = rank; dim-- > 0` 设备代码的误处理。`mvdr` 和 `coherence` 的候选 accuracy 用例原容差低于 float32 CPU/reference 本身误差，迁移时按 CPU reference 与 ZQ500 GPU 的实际误差重新校准 manifest，不改变算子实现。

5. 把测试入口从“单点手工复验”改为阶段化统一脚本。Stage1 负责平台打通、主库、Task1/Task2 L3、Python 图件；Stage2 负责 Task1/Task2 依赖算子 29/29 和 L1-L6 scale sweep；Stage3 负责全量公开算子 accuracy，从 53 条 active 扩展到 81 条，原注释候选全部纳入；Stage4 负责性能、资源、timing、全量 benchmark 和图件；Stage5 负责交付固化。`run_all_tests.sh --platform ZHONGKEXIN` 自动加载 SDK 并传入中科芯 CMake 参数，Stage3/Stage4 包装脚本生成 JSON/Markdown/CSV 报告和失败下钻日志。

6. 重新校准性能与规模策略。Task1/Task2 的 timing gate 原来按 A100 口径设置，中科芯 ZQ500 上会出现功能正确但 timing gate 误失败，因此只在中科芯平台下校准 Task2 L1/L2/L3 等阈值，并保留硬上限。benchmark 侧为所有 81 个算子补齐 scale mapping；`chebwin`、`firwin2` 等在默认大规模下触发中科芯资源限制的算子使用保守规模族，保证 L1-L6 可复现。最终 Stage4 full 生成 486 行 benchmark，失败 0 行，并生成 87 个 benchmark 图件文件。

最终验证结果：

- V4.1：平台打通、Task1/Task2、Python 依赖、可视化图件通过。
- V4.2：Task1/Task2 依赖算子 `29/29` 通过，Task1/Task2 L1-L6 全规模通过。
- V4.3：全量公开算子 accuracy `81/81` 通过。
- V4.4：Stage4 full 通过，81 个算子、486/486 行 benchmark 通过，图件生成通过。
- V4.5：README、AGENT、迁移状态、台账和交付文档收敛完成，当前项目可按单一中科芯 Stage4 full 命令复现交付基线。

后续向其他人说明时，可以把迁移归纳为三句话：第一，构建层从 NVIDIA CUDA/CMake 语言模型切换为中科芯 `dlcc` CXX 编译模型；第二，库和算法层对中科芯 FFT/SOLVER/runtime 差异做了平台分支和保守规模策略；第三，验证层用 CPU reference + ZQ500 GPU 的阶段化脚本关闭全部功能、报告、图件和 benchmark。

- 每个阶段结束前，必须检查本阶段发现项是否全部入账。
