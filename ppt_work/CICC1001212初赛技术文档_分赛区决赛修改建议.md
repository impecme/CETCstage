# 《CICC1001212 初赛技术文档》分赛区决赛修改建议

## 0. 审核范围与使用方式

**审核对象**：`ppt_work/CICC1001212初赛技术文档.docx`，共 103 页。  
**目标版本**：面向中科芯 ZQ500 平台的分赛区决赛技术文档。  
**原则**：本文件只说明如何修改；不改动原始 Word 文档，也不建议把初赛 CUDA 数据直接改名后继续使用。

本建议以当前仓库、两条任务的正式结构化报告和最终答辩 PPT 为准。发布前，所有数值都应从同一批 `data/reports/` 文件读取；不得手工沿用旧表格中的 NVIDIA/A100 数据。

### 0.1 必须先完成的全局替换

旧文档仍有大量初赛语境：`CUDA` 129 处、`NVIDIA` 8 处、`A100` 1 处、`cusignal_cuda` 4 处、`src/cuda` 2 处、`CudaReal* / CudaComplex*` 48 处，以及“第二阶段”“未实测”等表述。它们不能只做文字替换，必须连同工程事实一起重写。

| 初赛表述 | 决赛应改为 | 说明 |
|---|---|---|
| NVIDIA GPU / CUDA 第一阶段基线 | 中科芯 ZQ500 GPU 实测后端 | 不再写“后续迁移”“尚未实测”。 |
| `src/cuda/` | `src/zhongkexin/` | 当前 GPU 后端真实目录。 |
| `cusignal_cuda` | `cusignal_zx_gpu` | 当前 CMake 静态库目标。 |
| `CudaRealSignal`、`CudaComplexArray` 等 | `ZxGpuRealSignal`、`ZxGpuComplexArray` 等 | 以 `include/cusignal/core/types.hpp` 的实际类型为准。 |
| CUDA Runtime / cuFFT / cuBLAS / cuSOLVER | **ZQ500 CUDA 兼容 SDK 接口**；运行时、`dlFFT`、`dlBLAS`、`dlSolver` | 源码中保留 `cuda*` / `cufft*` / `cublas*` / `cusolver*` 兼容 API 名称，但 CMake 实际解析 ZQ500 SDK 库 `curt`、`dlfft`、`dlblas`、`dlsolver`。不能称为“在 NVIDIA GPU 上调用 cuFFT”。 |

| “第二阶段迁移计划” | “ZQ500 兼容适配实现与剩余优化方向” | 平台适配已经完成；后续内容只讨论性能和工程改进。 |

### 0.2 所有性能数字的统一口径

文档前言、任务结果、性能分析、亮点和附录必须采用同一口径：

```text
CPU/GPU 加速比 = CPU median total ÷ GPU E2E median total
GPU E2E 耗时   = GPU 调用端到端耗时
GPU kernel 耗时 = CUDA-event 记录的设备端 kernel 时间
```

当前正式 L6 报告中的可用数字为：

| 任务 | CPU total | GPU E2E total | CPU/GPU 加速比 | 来源 |
|---|---:|---:|---:|---|
| Task1 | 376.0365 ms | 11.5608 ms | 32.526858× | `data/reports/demo/task1_radar/scales/L6/metrics.json` |
| Task2 | 28595.4000 ms | 27.1477 ms | 1053.326801× | `data/reports/demo/task2_features/scales/L6/metrics.json` |

Word 中可分别按两位小数写为 **32.52×**、**1053.32×**，与最终 PPT 一致。不要引用旧文档中的 `24.160×`、`80.670×`、`31770.3×`、`NVIDIA A100-SXM4-40GB` 等初赛数字。

“GPU 优化前后提速”目前没有同规模 Git 基线的正式复测数据：如保留这一列，只能写 `待同规模基线复测补齐` 或 `X×`，不能以 CPU/GPU 加速比代替。

> 当前瓶颈主要集中在四类：第一，任务一输入构造和二维模糊函数仍受工作区和 tile 调度影响；第二，任务二 CWT 与谱图评分具有较高的多尺度/多分段计算量；第三，小规模算子容易受 kernel launch 和固定准备开销限制；第四，不同 shape 对 ZQ500 的资源利用率不同，需要继续积累形状特化和参数调优数据。

#### 6.5 后续方向

**替换为：**

> 后续优化与当前瓶颈一一对应：①算法与任务层，压缩任务一输入准备和模糊函数中间工作区，优化任务二 CWT 尺度与批量大小；②kernel 层，融合相邻轻量步骤，减少 launch，扩展固定 shape 特化路径；③显存层，优化数据布局、向量化访问、Tile 尺寸和 workspace 生命周期；④工程与平台层，建立 ZQ500 后端的参数自动调优和同规模基线复测流程。GPU 优化前后提速倍率必须在同一输入、同一计时口径的 Git 基线复测完成后补充，不能用 CPU/GPU 加速比替代。

#### 7.3 库级代表性机制

**删除**以 CUB、旧 MVDR、chebwin 旧数字为主体的内容，依次粘贴以下三小节：

> **（1）Wiener：Tile/Halo 邻域复用。** Wiener 需要在每个输出位置统计局部窗口的均值和方差，若每个线程独立从全局内存读取整个窗口，相邻输出会重复访问大量重叠数据。ZQ500 GPU 的二维固定窗口路径将一个输出 block 所需的中心区和 Halo 区协作加载到 shared memory；每个线程再从共享 tile 计算本地窗口统计。该方法将相邻窗口的重复全局读取转化为块内复用。正式性能 case 中，Wiener GPU E2E 耗时为 3.493 ms，CPU/GPU 加速比为 185.51×。
>
> **（2）Lomb-Scargle：频率对并行与共享归约。** Lomb-Scargle 对每个频率都需要遍历全部样本累加正弦、余弦及相关项，直接双重循环并行度不足且归约开销高。当前实现以频率对为并行单位，线程分片累加样本项，再在 shared memory 中做块内归约，从而提高每个 block 的有效工作量并减少全局归约。正式性能 case 中，Lomb-Scargle GPU E2E 耗时为 11.574 ms，CPU/GPU 加速比为 186.32×。
>
> **（3）Channelize Poly：形状感知分派与 8 通道特化。** 通用多相通道化器需要处理不同通道数、滤波器长度和输入规模；若所有形状均走通用路径，会重复计算旋转因子并产生额外分支。当前实现首先依据输入规模、数据布局、算法参数和正确性条件选择路径；当 `n_chans=8` 时启用专用 kernel，在 shared memory 中复用旋转因子，减少通用路径的重复开销。正式性能 case 中，Channelize Poly GPU E2E 耗时为 2.321 ms，CPU/GPU 加速比为 139.87×。

### 16.4 P0：Task2 的“mixed”含义必须如实解释

**核对结果：**Task2 有 8 个计算步骤，审计把它们标为 `mixed`。这不代表绕开算子库；也不代表 GPU 主链的每一帧、每一阶段都直接调用一个完整公开算子对象。真实结构是：公开算子定义滤波、解调、相关、spectrogram、CWT、B 样条、极值和 Kalman 的语义；任务 helper 为批量评分、投影、归一化、融合和紧凑输出服务；代表帧调用公开算子得到完整输出，用于 CPU/GPU 对照。

**特别修正三个容易写错的位置：**

| 步骤 | 不可写成 | 应写成 |
|---|---|---|
| spectrogram | “所有帧都 materialize 完整 spectrogram 后再求频带能量” | “主链按条件走固定 FFT 或直接频带能量评分；代表帧保留公开 spectrogram 输出核验” |
| CWT | “所有帧保留完整尺度×位置复数张量” | “主链保留每个位置的最大尺度评分；代表帧保留完整公开 CWT 结果” |
| measurement conversion | “GPU 额外复制 peak_track 生成 measurement_values” | “当前 GPU 主链将 `measurement_values` 直接别名为 `peak_track`，该步骤计时为 0；任务步骤 schema 仍保留该步骤以保持 CPU/GPU 对照结构” |

**替换任务二方法说明中的相关段落：**

> 任务二的 GPU 路径采用 mixed 实现：公共算子定义各信号处理阶段的输入输出语义，任务 helper 将多帧计算改写为批量评分、归一化、投影和融合。主链不物化对任务无用的完整中间张量；同时选取代表帧运行公开 `firfilter`、`correlate`、`spectrogram` 和 `cwt`，用于保留可对照的完整结果。该组织方式既满足公共算子语义与任务步骤契约，也避免批量任务中重复写回大中间数组。

### 16.7 P1：稳定性数据要区分“重复漂移”与“首次工作区占用”

初赛文档若只写“GPU free drift 为 0 MiB”，容易误导为任务不占显存。当前 L6 正式报告表明：

| 指标 | Task1 L6 | Task2 L6 | 正确解释 |
|---|---:|---:|---|
| 重复运行 free-memory drift | 0 MiB | 0 MiB | warm-up 后各重复轮之间没有持续泄漏 |
| RSS current drift | 7.96875 MiB | 4.22266 MiB | 重复轮间稳定，低于 64 MiB 门限 |
| 运行前后 GPU free delta | -192 MiB | -112 MiB | workspace/cache 首次建立后的常驻占用，不等于泄漏 |
| 运行前后 RSS delta | 520.508 MiB | 401.914 MiB | 进程工作集扩张，不能与重复轮 drift 混为一谈 |

**替换稳定性结论为：**

> L6 重复运行中，Task1 与 Task2 的 GPU free-memory drift 均为 0 MiB，RSS current drift 分别为 7.96875 MiB 和 4.22266 MiB，均通过既定门限。这说明 warm-up 后未观察到持续资源泄漏；同时，首次运行会建立 workspace 和缓存，因此运行前后资源差值应解释为常驻工作区占用，不应与重复运行漂移混用。

### 16.8 P1：必须写清 C++ 接口的兼容边界，避免“完整 cuSignal”等价迁移
