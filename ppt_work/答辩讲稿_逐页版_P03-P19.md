## P03｜赛题重述：库、平台、任务、验证

**衔接**：团队与项目角色介绍完成后，先界定本赛题的交付边界。

**讲稿**

本赛题的交付对象不是某一个孤立的 GPU kernel，而是一套能够在 ZQ500 上运行、且与 CPU reference 保持一致语义的 C++17 信号处理算子库。

右侧流程对应完整交付闭环：Host 端信号与参数经统一公开接口进入公共算子库；随后 CPU reference 与 ZQ500 GPU 使用同一接口，分别执行 Task1 雷达检测和 Task2 特征融合与跟踪；最后将两条任务的 CPU/GPU 结果汇合，对照正确性、性能并形成可追溯报告。

因此，项目同时解决四个问题：81 个公开算子的库覆盖、ZQ500 并行执行、两条端到端任务构建，以及统一验证。后续技术内容围绕这四个交付层展开。

**转场**：要保证 CPU/GPU 可对照，首先必须把接口、共享语义和后端边界固定下来。

## P04｜代码架构：统一语义、双后端实现

**讲稿**

代码架构分为三层。

第一层是公开 API，负责聚合头文件、核心类型和模块声明，对上提供一致的调用入口。第二层是共享语义层，集中约束参数、shape、axis 和数值规则；这使 CPU 和 GPU 后端不是两套相互独立的算法定义。第三层是双后端实现：`src/cpu` 提供 CPU reference，`src/zhongkexin` 提供 ZQ500 的 kernel、FFT、BLAS 和 Solver 实现。

两条任务均建立在同一套公开接口和共享语义之上。Task2 的私有 helper 只承担 batch、score 和 track 的任务级组织，不构成第三套计算后端。右侧预留区直接放 README 的真实目录树，用于证明架构与仓库一致。

这套分层的意义是：先用共享语义保证“算得对”，再让两个后端在相同语义下比较“算得快不快”。

**转场**：在统一架构之上，我们没有为每个算子孤立调参，而是抽象出可复用的公共机制和两条应用构建路径。

## P05｜技术路线：3 类公共机制、2 条应用、5 类路径

**讲稿**

本项目的技术路线概括为“3 类公共机制、2 条应用构建、5 类组合路径”。

左侧是面向单算子、可跨模块复用的三类机制：访存与资源复用、并行结构重构、shape-aware 分派与算子内 Fusion。它们分别处理三类典型障碍：相邻数据的重复访问、递归和归约依赖、以及频谱和中间结果的冗余计算。

右侧是应用级构建。Task1 将公开算子组织为雷达检测链；Task2 在调用算子库的基础上，结合 batch 和 score-only 私有 helper 构建特征融合与跟踪链。两条任务都沿数据驻留、复用、并行归约、融合/裁剪和结果紧凑回传等路径组合优化。

因此，下面三页先解释公共机制如何改变单算子的执行结构；之后再说明这些机制如何在两条任务中组合落地。

**转场**：第一类公共机制面对的是邻域算子最常见的瓶颈——大量相邻窗口反复读取同一批数据。

## P06｜公共机制一：Tile/Halo 访存复用

**讲稿**

以 Wiener 为代表的邻域滤波中，每个输出点都需要访问周围窗口。若每个线程直接从 global memory 读取窗口，相邻输出会重复读取大量重叠数据，GPU 的并行线程反而放大了显存访问压力。

我们的做法是将输出区域切分为 Tile，并把边缘所需的 Halo 一并协作加载到 shared memory。随后 Tile 内多个输出复用同一份局部数据：重复全局读取被转化为一次块内加载、多次块内访问。页面中的色块与 Halo 边界展示的正是这一数据复用关系。

除数据复用外，DeviceStorage 容量复用、prepared plan/table 缓存和精确 Host 内容缓存减少重复分配、重复准备和重复上传。它们共同服务于同一目标：把固定准备成本摊销到更多有效计算上。

页面展示的 Wiener 代表路径为历史整体路径对比，只说明这一优化组合在适用条件下的端到端效果，不能拆解为某一项机制的独立收益。二维奇数窗口等条件不满足时仍保留通用回退路径。

**转场**：邻域问题可以通过数据复用缓解；而 IIR 的难点不同，它的核心障碍是前后样本的递归依赖。

## P07｜公共机制二：Affine Scan 并行结构重构

**讲稿**

IIR 的原始递推中，当前输出依赖前一时刻状态。直接按样本展开时，后一项必须等待前一项完成，无法形成有效的 GPU 并行度；单纯增加线程数不能消除这种数据依赖。

我们先把递推状态改写为可结合的 affine transform。这样，每个数据块可以独立形成状态变换；块内采用 scan 并行组合，块间再对变换进行 scan，随后传播初态并行回代。原本“逐点串行”的过程被改写为“块内并行、块间分层合并”的结构。

关键不在于把循环直接搬到 GPU，而在于先改变数学表达，使依赖关系满足并行前缀计算的结合规律。页面中的四阶段结构对应状态变换、块内 scan、块间 scan 和结果回代。

同样，页面中的 lfilter 数据是历史整体路径对比，只用于说明这种结构重写的代表性效果。低阶、长序列最容易释放并行度；高阶、多线或短序列仍可能因状态规模和固定开销进入通用路径。

**转场**：前两类机制分别减少重复访存、重构递归依赖；第三类机制进一步处理频域计算中不必要的计算与写回。

## P08｜公共机制三：Shape-aware 分派与算子内 Fusion

**讲稿**

以 Periodogram 为例，传统频谱流程通常按复数 FFT 计算完整双边频谱，再进行幅值、归一化和频率筛选。对于实输入，这会计算本来由共轭对称决定的负频率部分，并产生多次中间写回和额外 kernel launch。

这里首先按输入 shape 和数据类型分派路径：实输入选择 R2C FFT，只保留有效半谱；随后将窗函数、频谱后处理和 PSD 计算在算子内衔接，减少中间张量的 materialize、global write 和 launch。复数或不满足数值约束的场景保留 C2C 通用路径，保证语义不被优化条件破坏。

因此，这一页的结论是：优化不是无条件合并所有步骤，而是在 shape-aware 的前提下选择正确路径，并只融合能够保持数值语义的相邻步骤。页面中的代表数据仍为历史整体路径对比，不与后续正式规模曲线混算。

**转场**：三类机制说明了单算子如何改变执行结构。下一部分需要回答：这些能力是否覆盖到完整公共算子库，并且在不同层次的算子集合中表现如何。

## P12｜Task1：公开算子驻留组合的雷达检测链

**讲稿**

Task1 的原则是：六个正式步骤均调用公开算子库的 GPU 实现，不以任务私有 kernel 绕开算子库。输入在入口转换为 Device 数据后，算子输出继续作为下游 Device 输入，只在验证边界统一回传，从而避免“每调用一个算子就 Host/Device 往返一次”的冗余。

围绕雷达检测链，页面展示了五类组合优化。模板 FFT 内容复用避免重复准备；scale 与 transpose/shift 融合直写减少中间张量；CFAR 使用 row-prefix 组织窗口统计；peak 采用两级 reduction；最终 detection list 以紧凑形式回传。

这条链的核心不是把所有步骤强行合并，而是保持每一步仍由公共算子实现，同时让数据、准备资源和中间结果在 Device 端连续流动。

**转场**：流程设计解释了 Task1 如何减少冗余；下一页用统一 L1～L6 规模实验验证这种公开算子组合是否形成稳定的端到端收益。

## P13｜Task1：统一 L1～L6 端到端性能

**讲稿**

Task1 的 L1～L6 实验固定模板、FFT、Hann、CFAR 和公开算子链，只改变输入规模。因此曲线反映的是规模对并行度和固定开销的影响，而不是混入 block、阈值或算法配置变化。

结果显示，Task1 在全部规模点均保持显著加速；L6 中 CPU total 为 364.798 毫秒，ZQ500 GPU total 为 11.023 毫秒，加速比直接计算为 33.09 倍。随着规模变化，加速比在固定开销和可利用并行度之间波动，这正是端到端任务的正常特征。

性能成立的前提是结果正确：L6 的 Expected、CPU、GPU 检测位置一致，CFAR 误差为 0.276398，小于 0.5。每点按统一重复协议统计，首轮 warm-up 不纳入中位数。

**转场**：Task1 是公开算子链的驻留组合；Task2 的数据规模和中间量更大，需要进一步从任务语义上裁剪无效计算。

## P14｜Task2：Batched Score-Only 特征融合与跟踪

**讲稿**

Task2 面临的主要问题不是单个算子能否执行，而是如果逐帧物化完整相关结果、谱图和小波张量，会带来大量中间数据、全局写回和链路同步。

因此，Task2 采用 batched score-only 结构。数据按 batch 驻留在 Device 端，相关、频域和小波路径只保留后续融合所需的 score，而不是保存完整中间张量；随后完成融合、peak 和 Kalman 更新，链尾只输出紧凑 track。

任务中的 correlate、spectral 等仍通过算子库路径调用；预编译 helper 负责 batch 组织和 score/track 特化，不是新的计算后端。这样既保持算子库边界，又从任务语义上删除不会影响最终跟踪结果的中间量。

**转场**：score-only 的价值在于减少无效物化。下一页以统一规模曲线验证，随着 batch 增大，这种结构能否充分释放 GPU 并行度。

## P15｜Task2：统一 L1～L6 端到端性能

**讲稿**

Task2 的 L1～L6 实验固定 score-only 语义、特征与轨迹门限，仅改变输入帧规模。因而性能曲线直接说明 batch 并行度和中间量裁剪对端到端总时间的作用。

在 L6，CPU total 为 28363.050 毫秒，ZQ500 GPU total 为 27.044 毫秒，加速比为 1048.78 倍。随着规模增大，GPU 的 batch 并行度得到更充分利用，score-only 避免的中间量也随之放大，因此端到端收益显著提升。

同样先验证语义再解释性能：CPU/GPU 的 peak track 一致，Kalman RMSE 为 0.477855，小于 2；feature-score mixed error 为 9.83703e-5，小于 1e-4。这里的对比对象仅为 CPU reference 与 ZQ500 GPU，不外推为与其他 GPU 的比较。

**转场**：两条任务分别给出了性能曲线和局部误差。下一页将把覆盖、运行步骤和关键误差放到同一验证框架中统一收束。

## P16｜正确性与运行验证：性能结论的前提

**讲稿**

性能提升只有在正确性通过的前提下才有意义。因此本页不再比较快慢，而是回答“结果是否可信”。

验证由三部分组成：第一，81 个公开算子均有性能记录；第二，两条端到端任务的 12 个正式 L1～L6 运行点和 14 个正式计算步骤均进入统一报告；第三，L6 分别检查任务关键语义。Task1 验证检测位置及 CFAR 误差，Task2 验证 peak track、一致性和特征误差。

这些覆盖、误差和性能均从同一运行报告读取。任何一项误差越过门限，或任一步骤未完成，均不能被标为 PASS。这样，后续对性能优缺点的判断才建立在可复现、可验证的结果之上。

## P17｜性能优缺点与改进方向：统一基线、单项参数对照

**讲稿**

目前的优势来自四类结构：Tile/Halo 将邻域重复读改为块内复用；Affine Scan 将递归依赖改为分层并行；R2C 与 Fusion 减少频谱冗余和中间写回；Device-resident 与 score-only 减少任务链回传和无效物化。

边界同样明确：部分算子受 global memory 带宽限制，部分多阶段路径仍有 kernel launch 开销，Kalman 等跨帧状态存在串行依赖，小规模输入则可能由固定开销主导。它们解释了为什么不是所有算子都会得到同等加速。

下一步先保持统一规模协议，只改变一个参数做单项参数对照：Tile/Halo 调整 block 与 halo；CFAR 调整 guard、reference、pfa；Task2 调整 batch 与 shape。最终以 L6 热点和三层算子性能图确定优先级，不把规模变化、算法参数和实现开关混在同一条曲线中。

**转场**：因此，项目的贡献不应表述为一串彼此无关的加速数字，而应归纳为三次可复用的结构性重写。

## P18｜核心亮点：从不适合 GPU 的结构到可执行结构

**讲稿**

第一个亮点是邻域访存重构：面对 Wiener 等相邻窗口重复读取，采用 Tile/Halo 将全局显存重复访问转化为 shared memory 内的数据复用。

第二个亮点是依赖与频谱重构：面对 IIR 的递归依赖，采用 Affine Scan 构造可分层并行的状态组合；面对实输入频谱的冗余计算，采用 R2C 与算子内 Fusion 仅保留有效半谱并减少写回。

第三个亮点是任务级语义裁剪：Task1 以公开算子链实现 Device 端驻留组合，Task2 以 score-only 只保留最终跟踪所需信息。两条路径共同避免把无用中间结果带到后续步骤。

三项亮点的共同逻辑是：不把原始 CPU 算法逐行搬到 GPU，而是先定位访存、依赖或中间量结构，再将其改写为 ZQ500 可并行执行的形式。

2. P09～P11 生成真实图后，每页只补读“一个代表算子或模块 + 加速/未加速计数 + 一句结构归因”；不得把 task27、extended28、core53 的数量或加速比相加、平均后宣称总收益。
3. P13、P15 的加速比统一按 `CPU median total / GPU median total` 直接计算；正确性数字必须与相应 L6 `metrics.json` 同源。
4. P17 的 block、halo、guard、reference、pfa、batch、shape 均是下一轮单项参数对照变量，未完成复测前不得表述为既有性能成果。
