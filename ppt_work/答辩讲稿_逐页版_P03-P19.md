## P03｜赛题重述

本赛题面向中科芯 ZQ500 平台，目标是构建一套同时兼顾 CPU reference 与 GPU 执行的 C++17 信号处理算子库。

交付不是单个算子的 GPU 加速，而是覆盖 12 个模块、81 个公开算子。在参数、shape、axis 和数值语义一致的前提下，完成雷达检测和特征融合与跟踪两条端到端任务，并输出正确性、性能和可追溯报告。

右侧流程展示了完整链路：Host 端输入通过统一公开接口进入公共算子库；CPU reference 与 ZQ500 GPU 使用同一接口分别执行；最终对两条任务的结果进行对照。

因此，后续汇报围绕四个层次展开：统一接口、GPU 并行算子、两条任务链，以及正确性和性能验证。

**转场**：先看代码如何将统一语义落实到 CPU 与 GPU 两个后端。

## P04｜整体代码库架构

代码库采用三层结构。

第一层是 `include/cusignal` 公开 API，统一聚合头、核心类型、模块声明和 ZQ500 兼容层；第二层是 `src/common` 共享语义层，集中规定参数、shape、axis 和数值规则；第三层是 CPU/GPU 双后端，`src/cpu` 作为 CPU reference，`src/zhongkexin` 负责 ZQ500 的 kernel、FFT、BLAS 与 Solver 实现。

两条任务均建立在这一公共接口之上。Task2 的 private helper 只负责 batch、score 和 track 的任务组织，仍然与公共算子路径协同。

右侧目录树对应仓库真实组织：从构建入口、公开头文件、双后端源码，到 demo、测试、数据报告和脚本，形成完整工程闭环。

## P05｜“3 + 2 + 5”技术路线

技术路线概括为“三类公共算子机制、两条应用任务链、五类任务级路径”。

左侧三类机制分别解决三类典型问题：访存与资源复用降低重复读取和准备开销；并行归约重构将串行双重循环改为高并行计算；形状感知分派与特化核针对满足条件的输入选择更高效的执行路径。对应代表算子的 CPU/GPU 加速比分别达到 185.51 倍、186.32 倍和 139.87 倍，基础算子最高达到 512.80 倍。

中间两条应用链分别是任务一雷达检测与任务二特征融合跟踪。在 L6 规模下，任务一达到约 32.5 倍，任务二达到约 1053 倍的 CPU/GPU 加速比。

右侧五类路径贯穿两条任务：设备驻留与批处理、准备与内容缓存、融合与直接写回、并行扫描与归约、仅评分与紧凑输出。公共机制提供单算子基础，任务链负责把它们组合为端到端能力。

**转场**：首先说明最常见的邻域访存问题如何通过块内复用解决。

## P06｜通用机制一：访存与资源复用

以 Wiener 为例，邻域滤波的相邻输出窗口存在大量重叠。如果每个线程都从全局内存重新读取窗口，同一输入会被多次读取，访存成为主要压力。

图中将 16×16 输出 Tile 连同 Halo 区域协作加载到共享内存。一次全局加载之后，多个输出 Tile 在块内复用这份数据，从“相邻窗口重复读取”转为“共享输入、多次输出”。

除 Tile/Halo 外，单算子内部还复用 capacity、prepared plan/table 和邻域输入：命中时直接执行，未命中时创建后复用，减少重复分配和重复准备。

Wiener 最终 GPU 耗时为 3.493 毫秒，CPU/GPU 加速比为 185.51 倍。页面中的“GPU 优化前后提速”暂以 `X×` 预留，待同规模基线复测后填入。

**转场**：访存复用解决了重复读取；对于双重循环，更关键的是把计算结构本身改造成适合 GPU 的并行形式。

## P07｜通用机制二：并行归约重构

Lomb-Scargle 的原始形式包含频率与样本的双重循环：频率逐个处理，每个频率又遍历全部样本，难以形成足够的 GPU 并行度。

我们的做法是将频率两两分配给线程块。块内线程对样本分片累加，再通过共享内存完成归约；最后得到对应频率的频谱功率。也就是将“频率逐个处理”的双重循环，重构为“频率对并行、线程分片累加、共享归约”的分层计算。

这一重构缩短了单个计算路径，同时释放多个频率对的并行度。代表算子 Lomb-Scargle 的最终 GPU 耗时为 11.574 毫秒，CPU/GPU 加速比为 186.32 倍；GPU 优化前后提速同样待基线复测后填写。

**转场**：前两类机制分别处理访存和循环结构，第三类机制进一步针对输入形状选择最合适的算子路径。

## P08｜通用机制三：形状感知分派与特化核

不同输入规模、内存布局、算法参数和平台条件，适合的 GPU 执行方式并不相同。因此，算子先经过路径选择，再从直接计算、分块共享内存、FFT/R2C、并行扫描或形状特化核中选择适用路径。

以 Channelize Poly 为例，通用逐通道方式会反复读取全局内存，并在每个通道重复计算旋转因子。对于“通道数等于 8 且点数达到规模阈值”的条件，切换到 8 通道特化核：Shared Twiddle 保存旋转因子，寄存器累加 8 个通道，并将结果直接写回通道矩阵。

这样将全局内存的多次读取与写回，压缩为一次读取、一次写回，同时通过循环展开减少重复计算。该代表路径最终 GPU 耗时为 2.321 毫秒，CPU/GPU 加速比为 139.87 倍。

## P10｜任务一：五类路径组合公开算子雷达检测链

任务一由六个公开算子组成雷达检测链。输入从主机一次上传后，在 GPU 端依次完成脉冲压缩、脉冲多普勒与频移、功率图、CA-CFAR 和最终检测；模糊函数曲面作为并行分支完成旁路质量分析。

这条链同时使用五类路径：第一，设备驻留，避免每一步在主机和设备之间往返；第二，模板与 FFT 预处理缓存；第三，将缩放、转置与频移直接融合写回；第四，对 CA-CFAR 使用行前缀扫描、对检测使用两级归约；第五，链尾只紧凑回传检测列表。

核心逻辑是让公开算子在 Device 端连续组合，减少重复上传、重复准备和中间结果物化。

## P11｜任务一：六种数据规模下的性能

本页以 L6 为例给出任务一各阶段的 CPU、GPU 与 GPU kernel 耗时，并在右侧给出 L1 到 L6 的 CPU/GPU 加速比。

从 L6 分项表可见，GPU 端的主要时间集中在输入构造、模糊函数和脉冲多普勒；脉冲压缩、功率图、CA-CFAR 和最终检测继续在同一条设备链上完成。GPU 总耗时与 kernel 耗时接近，也表明主要时间已集中在实际 GPU 计算。

## P12｜任务二：五类路径构建批量评分特征融合流程

上半部分是逐帧 CPU reference：每帧依次生成完整相关结果、完整谱图和完整 CWT，再进行峰值、关联和 Kalman 跟踪，会产生较大的二维、三维中间张量。

下半部分是 GPU Device-resident 路径。输入一次 H2D 后按 `B=8` 批处理；filter/demod、correlate、spectrogram 和 CWT 各分支只输出后续融合需要的 score，而不保留完整张量。之后完成加权平滑、行级 peak、Kalman 状态更新，最后紧凑输出 score、peak 和 state/track。

右侧五类路径对应设备驻留与批处理、相关与谱图预处理复用、各分支直接写入评分、频带评分与小波最大评分的并行归约，以及仅评分与紧凑输出。

这条任务链的关键是：从任务语义出发，删除不影响最终轨迹的全量中间张量物化。

## P13｜任务二：六种数据规模下的性能

本页同样以 L6 为例展示分项耗时，并给出 L1 到 L6 的加速比曲线。

在 L6 的 GPU 路径中，主要耗时集中在 CWT、输入构造和谱图计算；而 CPU reference 中，输入构造、相关和 CWT 的完整张量计算耗时很高。批量评分将这些路径压缩为 Device 端并行处理，并避免将完整中间量写出。

因此，随着规模增加，GPU 的批量并行度得到充分利用，L6 最优 CPU/GPU 加速比达到 1053.32 倍。该结果对应的是同一任务的 CPU reference 与 ZQ500 GPU 对比。

## P15｜核心亮点：三类结构重构策略

第一个亮点是邻域访存重构。面对相邻窗口的重复读取，通过 Tile/Halo 协作加载，让多个输出在块内复用共享输入。

第二个亮点是频率归约重构。面对长状态链或串行双重循环，通过频率对并行与共享归约缩短计算路径、提高并行度。

第三个亮点是任务输出重构。面对完整中间张量物化，通过设备驻留和仅评分策略，只保留最终需要的 score、峰值和轨迹。

三类策略分别作用于邻域访存、频率计算和任务输出，但共同目标一致：将原本不利于 GPU 的数据访问、循环组织和中间结果，重构为可解释的端到端 GPU 执行结构。
